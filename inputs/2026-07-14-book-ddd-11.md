# CQRS

Command Query Responsibility Segregation
상태 변경을 위한 (command) 모델과 조회를 위한 (query) 모델을 분리하는 패턴

- 도메인이 복잡할수록 명령 기능과 조회 기능이 다루는 데이터 범위에 차이가 나기 때문에 분리
- 두 모델을 분리하기 때문에 각 모델에 맞는 구현 기술 선택 가능: e.g. 명령 - JPA & RDBMS, 조회 - MyBatis & NoSQL
  - 조회 성능을 높이기 위해 메모리에 데이터를 저장하는 등의 방식을 하다보면 자연스럽게 CQRS가 되는 경우도 많음
- DB를 분리하게 되는 경우, 데이터 동기화는 이벤트를 활용해 처리
  - 상태 변경 이벤트 발생 -> 조회 모델에 변경 내역 반영
  - 모델 간 동기화가 중요한 경우 글로벌 트랜잭션을 사용
- 장점: 각 모델 구현 시 도메인 자체에 집중 가능, 조회 성능 향상시키는데 유리
- 단점
  - 구현할 코드의 증가. 도메인이 단순하거나 트래픽이 많지 않으면 CQRS 패턴을 갈 이유가 없을 수도 있음
  - 구현 기술이 더 많이 필요해 유지 보수 비용이 증가
