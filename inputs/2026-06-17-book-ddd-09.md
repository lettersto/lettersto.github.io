# Chapter 9. 도메인 모델과 바운디드 컨텍스트

## 1. bounded context (바운디드 컨텍스트)

- 모델은 특정한 컨텍스트 하에서 의미를 완전히 갖기 때문에, 때문에 한 개의 도메인으로 모든 하위 도메인을 표현하려고 하는 것은 불가능
- 논리적으로 같은 존재이지만 하위 도메인에 따라 다른 용어를 사용하는 경우도 있음
  - (예) 회원 - 상품, 검색 - 문서
- 바운디드 컨텍스트는 모델의 경계를 결정하는 컨텍스트를 의미한다.
- 바운디드 컨텍스트가 팀 조직 구조에 따라 결정되기도 한다. 팀 별로 다른 컨텍스트가 발생하는 것.
- 바운디드 컨텍스트를 고려하지 않고 하나의 도메인으로 만드려고 하면, 이후 확장하기 어려워질 수 있음

### 1-1. 도메인 영역 vs. bounded context vs. aggregate

* 도메인 영역: 다루는 비즈니스 문제
  * (예) 쇼핑몰 서비스: 주문, 결제, 배송, 상품, 회원 등
  * 코드보다는 실제 비즈니스의 업무 영역의 구분에 가까움
* 바운디드 컨텍스트: 어떤 맥락, 의미 체계 안에서 모델을 정의하는가
  * 용어가 유효한 경계. 모델의 의미가 일관되게 유지되는 경계.
  * (예) 상품의 의미
    * 상품 컨텍스트: 이름, 설명, 이미지, 카테고리 등
    * 주문 컨텍스트: 주문 시 상품명, 가격, 수량 등
    * 재고 컨텍스트: 상품의 창고 위치, 가용 수량 등
    * => 똑같은 상품이지만 각 컨텍스트에서 필요한 속성, 규칙이 다름. 하나의 거대한 Product 모델이 아니라, 컨텍스트 별로 다른 모델 생성
* 애그리거트: 일관성을 지켜야하는 객체 묶음의 단위
  * 도메인 객체의 일관성 단위.
  * 상위 도메인 모델을 수정하면 -> 어떤 하위 도메인 모델까지 영향력이 전파되는가?
  * 어떤 객체들을 한 트랜잭션 안에서 함께 변경해야 하는가? 외부에서는 어떤 루트 애그리거트를 통해서만 접근해야 하는가?
  * 비즈니스 로직을 지키는 단위

```
도메인
 ├─ 주문 서브도메인  // 1개 서브 도메인에 여러 바운디드 컨텍스트도 가능
 │   └─ 주문 바운디드 컨텍스트
 │       ├─ Order 애그리거트
 │       ├─ Cart 애그리거트
 │       └─ ReturnRequest 애그리거트
 │
 ├─ 결제 서브도메인
 │   └─ 결제 바운디드 컨텍스트
 │       ├─ Payment 애그리거트
 │       └─ Refund 애그리거트
 │
 └─ 배송 서브도메인
     └─ 배송 바운디드 컨텍스트
         ├─ Shipment 애그리거트
         └─ DeliveryTracking 애그리거트
```



## 2. 바운디드 컨텍스트 구현

- 바운디드 컨텍스트 구성: 도미엔 모델 + 표현 영역, 응용 서비스, 인프라 스트럭처, 테이블
- 각 바운디드 컨텍스트는 다른 조회 패턴, 다른 구현 기술을 사용 가능.
- 두 바운디드 컨텍스트 간 통합 방법
  - REST API를 호출
    - (예) 추천 시스템에서 추천할 상품(추천 바운디드 컨텍스트)를 REST API로 받아와서 쇼핑 서비스(카탈로그 바운디드 컨텍스트)에서 받아온 목록을 변환하여 사용.
    - MSA가 바운디드 컨텍스트와 잘 어울리는 이유: 바운디드 컨텍스트마다 프로젝트를 만들게 되고, 코드 수준에서 두 컨텍스트를 분리하기 때문에, 두 바운디드 컨텍스트 간 모델이 섞이지 않도록 한다.
- 공유 커널(shared kernel): 두 바운디드 컨텍스트가 같은 모델을 공유하는 경우
  - (예) 주문: 고객을 위한 서비스 & 운영자를 위한 운영 툴에서의 주문
  - 중복 설계를 막는데 도움
  - 두 컨텍스트 모두 모델을 변경하지 않는 상황에서 가능
- 독립 방식(seperate way): 서로 통합하지 않는 방식
  - 서로 독립적으로 모델 발전 시킴
  - 이후 두 컨텍스트 모델을 합쳐야 한다면, 두 시스템을 통합하기 위해 별도의 시스템을 만들어야 할 수도 있음
