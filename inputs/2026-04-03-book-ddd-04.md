# 4장 - 리포지터리와 모델 구현

책의 4장은 JPA 기술에 많은 의존을 하고 있다. 그래서 JPA를 사용하지 않는 입장에서 유용하다고 느낀 사항만 따로 정리했다.



---

리포지터리 **인터페이스**는 **도메인 영역**에 속하고,
리포지터리를 **구현**한 클래스는 **인프라스트럭처 영역**에 속한다.

가능하면 리포지터리 구현 클래스를 인프라스트럭처 영역에 위치시켜서, 코드의 인프라스트럭처에 대한 의존을 낮춰야 한다.



그런데 JPA 기술 인프라스트럭처 영역이다. JPA의 `@Entity`, `@Table` 등을 도메인 모델에 붙여서 사용하게 된다. 즉, 도메인 영역이 인프라에 의존하게 되는 것이다. 즉, DIP 원칙을 어기게 된다.

```java
@Entity  // JPA
@Table(name="article")  // JPA
public class Article {  // 도메인
  @Id
  private Long id;
}
```

```java
public interface ArticleRepository extends Repository<Article, Long> {
  void save(Article article);
  Optional<Article> findById(Long Id);
}
```

물론, 구현 기술을 변경하도록 도메인이 받는 영향을 최소화하도록 도메인 영역과 인프라스트럭처 영역을 철저히 구분할 수 있다. 다만 구조가 복잡해지고 관리해야 할 코드가 늘어남을 알 수 있다.

```java
// domain/Article.java
public class Article {
    private Long id;
    private String title;
    private String content;

    public Article(Long id, String title, String content) {
        this.id = id;
        this.title = title;
        this.content = content;
    }
}
```

```java
// domain/ArticleRepository.java
public interface ArticleRepository {
    Article findById(Long id);
    void save(Article article);
}
```

```java
// infrastructure/ArticleJpaEntity.java
// @Entity와 같이 JPA annotation을 붙이는 entity를 별개로 구현
@Entity
@Table(name = "article")
public class ArticleJpaEntity {
    @Id
    private Long id;
    private String title;
    private String content;

    // 도메인 → JPA 변환
    public static ArticleJpaEntity fromDomain(Article article) {
        ArticleJpaEntity entity = new ArticleJpaEntity();
        entity.id = article.getId();
        entity.title = article.getTitle();
        entity.content = article.getContent();
        return entity;
    }

    // JPA → 도메인 변환
    public Article toDomain() {
        return new Article(id, title, content);
    }
}
```

```java
// Repostiory 구현
// infrastructure/ArticleJpaRepository.java
public interface ArticleJpaRepository extends JpaRepository<ArticleJpaEntity, Long> {}
```



DIP를 사용하는 주된 이유는 저수준 구현이 변경되더라도 고수준이 영향을 받지 않기 위함이다. 하지만, 실제로 운영하다보면 이 저수준 구현이 변경될 일은 거의 없다. 이렇게 변경이 거의 없는 상황에서 변경을 미리 대비하는 것은 과할 수도 있다. 그러므로 서비스 상황에 맞게 적절히 타협해야 한다.



→ 맞는 말이다. 실제로도 저수준 구현의 변경으로는 DB 변경으로 아직까지 딱 한 번만 경험해보았다. 다만 저수준과 고수준이 나뉘어 있음에도 불구하고 대규모 이사였던 것으로 기억한다.

1. 아무리 DIP를 이용해서 구현하더라도 사람인 이상 완벽하게 둘을 분리하는 것은 어렵다.
2. DB마다 제공하는 특징적인 기능이 있는데, 이를 사용하지 않기에는 아쉬울 때가 많다.
   (예) Redis의 경우 SortedSet 등 다양한 자료구조를 지원한다.
3. 동일한 메서드(e.g. findById)를 똑같이 구현해도 DB에 따라 성능 차가 존재한다. 이 성능 차로 인해 옮겨갔을 때 문제가 발생할 수 있다.

저수준을 쉽게 갈아낄 수 있도록 구현되어 있음에도 불구하고, 이러한 문제가 많이 존재하는데 안 하면 더한 문제를 겪었을 지도 모른다. 그리고 의외로 개발자란 동일한 코드를 복붙해서 여러 프로젝트에 갖고 다니기 때문에, 다양한 DB에 만능으로 대처할 수 있는 것이 있다면 편리하다.

하지만 여태까지 단 한번의 저수준 교체 경험을 한만큼, DIP가 꼭 이득일까 하는 생각도 드는 것이다. 심지어 AI가 갈수록 코드를 짜주는 지금에 있어서는 더더욱 그렇다. 커스텀하게 구조를 분리해두면 그만큼 AI가 먹을 콘텍스트가 늘어난다.
