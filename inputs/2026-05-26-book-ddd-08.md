# Chapter 8. 애그리거트와 트랜잭션 관리

* Pessimistic Lock (선점 잠금)
* Optimistic Lock (비선점 잠금)
* Offline Pessimistic Lock (오프라인 선점 잠금)



## 1. Pessimistic Lock (선점 잠금)

* 애그리거트를 구한 스레드가 사용이 끝날 때까지 다른 스레드가 아예 해당 애그리거트를 수정하지 못하게 막는(blocking) 방식
* DB가 제공하는 행 단위 잠금을 이용해 구현
* 선점 중이면 다른 스레드는 Lock을 획득하지 못하고 실패
* 교착 상태 (deadlock)이 발생할 수 있음
  * 이를 막기 위해 lock 획득에 timeout을 걸어둬야 한다.
  * DB에 따라 이를 지원하기도 하고 안 하기도 하니 반드시 확인해보기

```
스레드 A가 애그리거트1 선점 중
스레드 B가 애그리거트2 선점 중
스레드 A가 애그리거트2를 선점하려고 함 -> 스레드 A대기
스레드 B가 애그리거트1을 선점하려고 함 -> 스레드 A, B 모두 대기
```



## 2. Optimistic Lock (비선점 잠금)

* 처음부터 한 자원에 동시에 접근하는 것 자체를 막는 대신, 변경한 데이터를 DB에 반영하는 시점에 변경 가능 여부를 다시 확인하는 방식
* 내가 수정하려는 시점에 다른 누군가가 수정하지는 않았는지 확인하고, 수정되어 있다면 실패하는 방식
* JPA에서는 보통 `@Version` 으로 구현
* 나중에 저장한 사람이 앞 사람이 저장한 내용을 인지하지 못한 채 덮어쓰게 되는 것을 방지하는데 초점



## 3. Offline Pessimistic Lock (오프라인 선점 잠금)

https://martinfowler.com/eaaCatalog/pessimisticOfflineLock.html?utm_source=chatgpt.com

* **여러 트랜잭션**(단일 트랜잭션 X)에 걸쳐서 동시 변경되는 것을 막는 잠금 방식
* **business transaction**: 실제 업무 단위의 트랜잭션

```
// 아래 과정 전체가 하나의 business transaction
사용자 A가 문서 수정 화면 진입
→ 5분 동안 문서 파악
→ 표 수정
→ 글 추가
→ 저장 버튼 클릭
```

위와 같은 한 business transaction 동안 계속 DB 트랜잭션을 열어두는 것은 불가능하다. DB 커넥션, 트랜잭션 리소스, 행 단위 Lock을 너무 오랫동안 점유하기 때문이다.

→ DB 트랜잭션(online)은 짧게 여러 개로 유지하되, **애플리케이션 레벨(offline)에서 별도의 잠금 상태**를 관리하는 것이 필요



\<DB와 offline pessimistic lock의 차이>

| 구분      | DB Pessimistic Lock        | Offline Pessimistic Lock                                |
| --------- | -------------------------- | ------------------------------------------------------- |
| 잠금 위치 | DB row/table lock          | 애플리케이션/별도 lock table/cache<br />Redis 등에 저장 |
| 사용 범위 | 하나의 짧은 DB transaction | 여러 요청에 걸친 긴 업무 transaction                    |
| 예시      | `SELECT ... FOR UPDATE`    | `document_lock`, `editing_lock` 테이블                  |
| 지속 시간 | 보통 ms~초 단위            | 수십 초~수 분 가능                                      |
| 목적      | 동시에 같은 row 갱신 방지  | 사용자가 수정 작업을 진행하는 동안 선점 보장            |

* 예를 들면 사용자가 문서 수정 작업을 시작할 때 문서 수정 작업 business transaction 전체에 대한 Lock을 얻는다.

```
A가 문서 편집 시작
문서가 A에게 잠김
B는 편집 버튼을 누르면 “A가 편집 중입니다” 표시
A가 저장/취소하면 B가 편집 가능
```

* 그런데 애플리케이션 단위의 Lock의 경우 Lock해제가 명시적이지 않을 수 있다. 유저가 수정 화면을 브라우저 창 단위로 닫아버리는 경우, 서비스에는 유저가 수정 화면을 종료했는지 안 했는지 알 수 없다.
  * 이때 다른 유저가 문서를 수정하려고 오면 문서의 Lock을 획득할 수 없다.
  * 그러므로 Offline pessimistic lock의 경우 lock timeout을 반드시 가지고, 유저가 활동하는 동안 계속해서 잠금 유효 시간을 갱신하는 방법으로 해야한다.



\<Lock 테이블 두는 방식으로 구현 가능>

```sql
CREATE TABLE offline_lock (
    resource_type VARCHAR(50) NOT NULL,
    resource_id BIGINT NOT NULL,
    locked_by VARCHAR(100) NOT NULL,  -- 대신 lock_id도 가능
    locked_at TIMESTAMP NOT NULL,
    expires_at TIMESTAMP NOT NULL,
    PRIMARY KEY (resource_type, resource_id)
);
```

```java
// lock 획득 방법
@Transactional
public void acquireLock(String resourceType, Long resourceId, String userId) {
    // 1. 만료된 lock 제거
    lockRepository.deleteExpiredLocks();

    // 2. 이미 잠겨 있는지 확인
    if (lockRepository.existsByResourceTypeAndResourceId(resourceType, resourceId)) {
        throw new AlreadyLockedException("현재 다른 사용자가 수정 중입니다.");
    }

    // 3. lock 생성
    lockRepository.save(new OfflineLock(
        resourceType,
        resourceId,
        userId,
        LocalDateTime.now(),
        LocalDateTime.now().plusMinutes(10)
    ));
}
```

```java
// 애그리거트 업데이트 방법
@Transactional
public void updateProduct(Long productId, ProductUpdateRequest request, String userId) {
    // 1. 내가 lock을 가지고 있는지 확인
    OfflineLock lock = lockRepository.findByResourceTypeAndResourceId("PRODUCT", productId)
        .orElseThrow(() -> new LockNotFoundException());

    if (!lock.isOwnedBy(userId)) {
        throw new NotLockOwnerException();
    }

    // 2. 실제 데이터 수정
    Product product = productRepository.findById(productId)
        .orElseThrow();

    product.update(request);

    // 3. lock 해제
    lockRepository.delete(lock);
}
```

* OT의 기본 아이디어는 “문서 전체를 덮어쓰기”가 아니라, 사용자의 편집을 이런 operation으로 표현하는 것입니다.

```
insert(position=5, text="hello")
delete(position=10, length=3)
format(range=3~8, bold=true)
```

* 사용자가 글자를 입력할 때마다 문서 전체를 DB에 덮어쓰는 것이 아니라, 먼저 operation을 서버에 보냅니다.

```
Client A → Server: doc=1, baseRev=100, op=insert(5, "hello")
Client B → Server: doc=1, baseRev=100, op=delete(3, 2)
```

* 서버는 문서별로 operation에 순서를 부여합니다.

```
seq=101: insert(5, "hello")
seq=102: delete(... transformed ...)
```

* 모든 사용자가 같은 최종 문서 상태에 도달합니다.
