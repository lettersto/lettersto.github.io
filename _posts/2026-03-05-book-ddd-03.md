## 1. 애그리거트 (Aggregate)
<br/>

*항상 함께 관리되어야 하는 객체들의 묶음*

서비스가 성장할수록 여러 도메인 객체가 발생하는데, 객체들이 서로를 직접 접근하게 되면 의존성이 높아지고 유지보수하기가 갈수록 어려워진다. 그렇기 때문에 애그리거트는 관련된 객체를 하나로 모아서 관리한다.

- 함께 관리되어야 하기 때문에 애그리거트 내부 객체는 라이프사이클(생성, 파괴 등)이 비슷하다.
- 한 애그리거트에 속한 객체는 다른 애그리거트에 속하지 않는다.
- 애그리거트 간 경계는 비즈니스 규칙이 기반이 된다.
  - (예) 주문 없이 주문상품 존재 불가 → 같은 애그리거트
  - (예) 주문이 없어도 상품 존재 가능 → 다른 애그리거트
- A 객체가 B 객체를 갖고 있다고 해서 A와 B가 반드시 하나의 애그리거트로 묶이는 것은 아니다.

## 2. 애그리거트 루트
<br/>

*애그리거트 내 모든 객체가 일관된 상태를 가지도록 관리하는 주체*

애그리거트는 여러 객체로 구성되기 때문에 한 객체의 상태가 변경되면, 다른 객체에도 모두 반영되어야 한다. 이를 관리하는 것이 **애그리거트 루트 엔터티**이다.

- 애그리거트 루트는 애그리거트가 제공해야 할 도메인 기능을 제공한다.
- 애그리거트 외부에서 내부 객체를 직접 변경하면 안 된다.
  - set 메서드를 public으로 만들지 않는 것으로 원천 차단 가능
  - 밸류 타입은 불변 권장
- 외부에서 애그리거트에 접근할 때 반드시 애그리거트 루트를 거쳐야 한다.

```java
class Member {  // 애그리거트 루트

    private Profile profile;  // 안에 속하는 객체

    public void changeNickname(String nickname) {
        profile.changeNickname(nickname);
    }
}

// 외부에서 접근 시 무조건 애그리거트 루트를 통해서만
member.changeNickname("newName");  // O

// 외부에서 접근할 때 애그리거트 내부 객체를 통하려고 하면 안 된다.
profile.changeNickname("newName");  // X
```

## 3. 리포지터리와 애그리거트
<br/>

*리포지터리는 애그리거트 단위로 존재한다.*

애그리거트는 개념상 완전한 한 개의 도메인 모델을 표현한다. 애그리거트 내부의 각 객체를 물리적으로 별도의 테이블에 저장한다 하더라도, 리포지터리는 한 개만 존재한다.

- 리포지터리 기본 메서드: `findById`, `save`
- RDBMS를 사용하는 경우: 트랜잭션을 이용해 한 애그리거트에서 발생한 변경이 각 객체에 동일하게 업데이트 되도록 보장
- NoSQL을 사용하는 경우: 한 테이블, 한 문서 등 애그리거트 단위로 통으로 저장하여 객체 간 상태가 일치하도록 저장

## 4. ID를 이용한 애그리거트 참조
<br/>

애그리거트가 다른 애그리거트를 참조하는 것은 가능하지만, 구현이 쉽다고 해서 필드의 형태로 직접 참조하는 것은 지양해야 한다. 한 애그리거트가 관리하는 범위는 자기 자신으로 한정해야 하기 때문이다.

### 4-1. 직접 참조 시 발생하는 문제
<br/>

- 다른 애그리거트의 상태를 쉽게 변경 가능해짐 → 의존 결합도 상승
- 성능 문제: 애그리거트가 들고 있는 정보가 많을 때 항상 eager 로딩을 하면 불필요한 객체를 함께 로딩하는 경우가 발생

```java
// 필드를 통한 직접 참조 예시
public class Order {
    private Member member;
}
```

### 4-2. ID를 이용한 간접 참조
<br/>

직접 참조 대신 ID를 이용한 참조를 사용한다. 일종의 외래키와 같은 개념이다.

- 애그리거트 간 직접적인 연결을 제거하여 모델의 복잡도를 낮춤
- 한 애그리거트에서 다른 애그리거트의 상태를 변경하는 것을 근본적으로 차단
- 구현 복잡도도 낮아짐: lazy와 eager 로딩 중 고민하지 않아도 됨

```java
// ID를 통한 간접 참조 예시
public class Order {
    private MemberId memberId;
}
```

### 4-3. N+1 조회 문제
<br/>

ID를 이용한 참조에서 발생할 수 있는 문제점이다. 조회 대상이 N개일 때, N개를 읽어오는 한 번의 쿼리와 연관된 데이터를 읽어오는 쿼리를 N번 실행하게 되어 전체 조회 속도가 느려진다.

예를 들어, 주문 리스트를 가져온 뒤 주문 리스트에 있는 제품 N개의 ID로 각 제품의 정보를 가져오는 경우가 이에 해당한다.

```java
// N+1 문제 발생 예시
// 주문 목록을 가져온 뒤, 각 주문의 제품 정보를 개별 조회 -> 쿼리 1 + N번
List<Order> orders = orderRepository.findByMemberId(memberId);  // 쿼리 1번
for (Order order : orders) {
    // 각 주문마다 제품 정보를 별도로 조회 -> 쿼리 N번
    Product product = productRepository.findById(order.getProductId());
}
```

이를 해결하려면 **조회 전용 쿼리**를 사용한다. 데이터 조회를 위한 별도 DAO를 만들고, DAO의 조회 메서드에서 조인을 이용해 한번의 쿼리로 필요한 데이터를 로드한다.

```java
// 조회 전용 DAO로 해결
public class OrderSummaryDao {
    public List<OrderSummary> findByMemberId(MemberId memberId) {
        // SELECT o.order_id, o.product_id, p.name, p.price
        // FROM orders o
        // JOIN product p ON o.product_id = p.product_id
        // WHERE o.member_id = ?
        // -> 쿼리 1번으로 해결
    }
}
```

## 5. 애그리거트 간 집합 연관
<br/>

애그리거트 간에는 1-N, M-N, N-1 관계가 존재한다. 사실상 모든 관계가 가능하다는 이야기인데, 핵심은 관계가 존재한다고 해서 Set, List 등으로 구현하지 않는다는 것이다.

> 애그리거트 간에는 독립적인 라이프사이클을 가져야 하므로, Set으로 직접 참조하면 경계가 흐려진다.
{: .prompt-info }

- 성능 문제: 1-N에서 N개를 전부 로딩하게 됨
- 결합도 증가: 한쪽 애그리거트 변경이 다른 쪽에 영향이 커짐

대안은 **ID 참조로 간접 연관**을 맺고, 필요할 때 repository에서 조회하는 것이다.

- 1-N 보다는 N-1을 이용하거나, 필요한 만큼 repository에서 조회해서 쓰는 방식을 이용한다 (pagination).
- M-N 관계는 RDBMS에서 join 테이블을 이용해 구현한다.

```java
// 1:N 관계 — Category가 Product를 Set으로 들고 있음 (X)
public class Category {
    public Set<Product> products;
}

// N:1 관계 — Product가 CategoryId만 들고 있음 (O)
// 카테고리별 상품 목록이 필요하면 repository에서 조회
public class Product {
    public CategoryId categoryId;
}
// productRepository.findByCategoryId(categoryId, page, size);

// M:N 관계 — Student와 Course
// 양쪽 다 Set으로 들고 있지 않고, ID 참조 + join 테이블로 구현
public class Student {
    public StudentId id;
}
public class Course {
    public CourseId id;
}
// RDBMS: student_course(student_id, course_id) join 테이블
// studentCourseRepository.findCourseIdsByStudentId(studentId);
```

## 6. 애그리거트를 팩토리 메서드로 사용
<br/>

*애그리거트가 갖고 있는 데이터를 이용해서 다른 애그리거트를 생성해야 할 때, 팩토리 메서드를 고려한다.*

A 애그리거트의 필드를 이용해 B 애그리거트를 생성하는 경우, 이 생성 로직을 A 애그리거트의 팩토리 메서드로 구현할 수 있다.

### 6-1. 문제: 응용 서비스에 도메인 로직 노출
<br/>

상품 신규 등록을 예시로 보면, Store와 Product 애그리거트가 존재하고 `RegisterProductService`라는 응용 서비스가 존재한다.

<small>*"상품 등록"이 응용 서비스인 이유: Repository 조회/저장(인프라 협력) + 차단여부 판단/상품 등록(도메인 로직)을 조합해서 실행하기 때문*</small>

현재 아래 코드에서는 product 생성 가능 여부가 Store의 내부 상태에 의해 결정됨에도 불구하고, 가게 상태 체크와 상품 생성이 응용 서비스에서 분리되어 작성되어 있다. 이렇게 되면 다른 개발자가 상품 등록 전에 가게 상태 체크를 빠뜨리는 코드를 작성할 수 있어서 도메인 규칙이 깨질 수 있다.

```java
// 가게에서 상품을 신규로 등록할 때 응용 서비스
public class RegisterProductService {
    public void registerNewProduct(NewProductReq req) {
        Store store = storeRepository.findById(req.getStoreId());

        // 1. store가 product를 신규 등록할 수 있는지 판단
        if (store.isBlocked()) {
            throw new StoreBlockedException();
        }

        // 2. product를 생성
        Integer storeId = store.getId();
        Product product = new Product(storeId);

        return;
    }
}
```

### 6-2. 해결: Store 애그리거트의 팩토리 메서드
<br/>

가게 신규 제품 등록 가능 여부 판단과 제품 생성은 모두 Store 애그리거트의 책임이다. Store 애그리거트 내부에 팩토리 메서드를 만들어서, 등록 가능 여부 확인과 생성이 항상 함께 실행되도록 한다.

```java
public class Store {
    public Product createProduct(...) {
        if (isBlocked()) {
            throw new StoreBlockedException();
        }
        return new Product(this.id);
    }
}
```
